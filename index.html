How I run a team

I lead a globally distributed team of eight, including two managers, and own the budget and vendor strategy for the governance tooling stack. I report outcomes quarterly to the CISO and CIO.

The organisational design I keep returning to is a narrow ownership boundary with real teeth: engineering teams own development and remediation, my team owns the checkpoint. That split works because it avoids the failure mode where a central team becomes a bottleneck everyone resents, and it only works if the checkpoint is fast. So I automated our own function first — AI-assisted tooling for application security review, vendor assessment and threat modelling now handles around twenty reviews a quarter and cut manual effort roughly 80%, and a compliance assistant built with Internal Audit cut audit effort about 60%.

Beyond the team: cross-functional authority across Legal, Compliance, Privacy, Data Platform, Security, Enterprise Risk and Internal Audit — which in practice means resolving competing priorities between groups with genuinely different incentives. I led technical due diligence on the acquisition of an agentic AI governance platform, defining control requirements across Security, Engineering and Finance, and have made build-versus-buy calls against a real budget after evaluating the field.

Agent harnesses design · evaluation · guardrails

Our internal agent runtime — orchestration, a tool and MCP registry, context and state management — was built by a partner team. I was part of the technical evaluation and design: what the registry had to enforce, where state could be trusted, which failure modes the architecture had to make structurally impossible rather than merely unlikely.

What I own is the layer that constrains it. An evaluation platform for vulnerabilities in agentic applications. An adversarial module that red-teams agents against prompt injection and jailbreak-style attacks, which I've run against production agentic surfaces before release. Inline policy enforcement in the request path, out-of-band prompt monitoring, and the pre-deployment scanner for external AI tooling described above. Plus response analysis that scores each lifecycle stage separately — query, retrieval, generation, answer.

That last detail is the one I'd argue hardest for. Most evaluation grades the final answer, which tells you that something went wrong but not where. Scoring each stage tells you whether the retrieval was thin, the generation overreached, or the plan was wrong from the first step — and those need completely different fixes.

Evidence first, then action

My working principle is that an agent should not be able to assert or act on anything it cannot point at. An unsourced claim isn't a stylistic weakness, it's a failure of the run, and the harness should treat it that way — surfacing the retrieval that justified each step, and stopping rather than proceeding when the evidence underneath a decision is thin. A system that guesses confidently is worse than one that halts, because the first kind erodes trust in every output it ever produced, including the correct ones.

Using the trace to decide where to look

This one is a design position rather than a shipped system — I haven't built it, and I want to be precise about what I think it can and can't do.

The appealing version is that an agent's execution trace tells you whether to trust its answer. I don't think that holds. A trace can look impeccable — good documents retrieved, every planned tool called, nothing retried — while the model quietly conflates two entities or misreads a figure. That may well be the most common real failure, and it leaves no mark on the trace at all. Timing is worse than useless as a proxy: latency is dominated by caching and provider variance, so scoring on it would penalise every optimisation the platform makes.

What the trace is good for is triage. Verification that actually works — checking each claim against a supporting span in the retrieved context — is far too expensive to run on everything. So the useful question isn't "is this answer true," it's "where should the expensive check go." A triage signal is allowed to be noisy in a way a confidence score isn't, and that difference is the whole design.

Three things I'd route on. An agent that absorbed a failure silently — a tool errored or came back empty and the run continued without acknowledging the gap — which is a genuine defect regardless of whether the output happens to be right. An answer asserting things on a task type that should have required grounding, where little or nothing was retrieved. And claims inherited across a handoff that arrive carrying no evidence of their own.

That last one is the failure I'd worry about most in multi-agent systems, and it's the piece I'd build first. Call it laundering: agent A guesses, agent B receives the guess as a plain fact, and by agent C it's load-bearing and unattributable. Uncertainty has to be inherited at the handoff rather than dropped, and abstention has to be a first-class outcome the system is rewarded for.

The method comes from work I've already done: fingerprinting applications from packet sizes, inter-arrival times and communication patterns without decrypting anything, and modelling device behaviour from NetFlow as a time series. An agent run has a comparable structure. I'd expect the transfer to be partial — agent task types are heterogeneous and shift under every model upgrade, where NetFlow gave you stationary behaviour across millions of devices — which is another reason to aim this at routing attention rather than at rendering verdicts.

Keeping harnesses from going overboard

The characteristic failure of agentic systems isn't that they refuse to work. It's that they keep going — widening scope, taking adjacent actions nobody asked for, chaining tool calls until something breaks in a way that's expensive to unwind. The instinct to fix this with better prompting is the wrong instinct. Prompt-level instruction is advisory; anything you actually need to hold belongs in the runtime, where the agent cannot argue with it.

  • Capability is scoped per task, not per agent. The tool registry is a control point, not a directory — access granted narrowly and for the duration of the work, so a compromised or confused agent inherits a small surface rather than the union of everything it might ever need.
  • Guardrails sit in the request path. Sensitive-data detection, masking and policy evaluation run inline, where they apply regardless of what the model was persuaded to believe.
  • Blast radius is bounded by construction. Step and cost budgets, explicit stop conditions, and a hard checkpoint before anything irreversible. Reversibility is a design property, not an operational hope.
  • Refusing to act is a valid outcome. Harnesses that cannot stop will not stop. Halting on insufficient evidence has to be a first-class result the system is rewarded for, not an error state it learns to route around.
  • The harness is the audit log. Every step leaves a record at the point it happens, because evidence reconstructed after an incident is evidence nobody trusts.
  • Friction has a budget too. Controls that make the sanctioned path slower than the workaround don't get followed, they get bypassed — which is why enforcement has to be measured on latency alongside coverage.

Those principles aren't theoretical caution. They're what I concluded from running adversarial testing against production agentic surfaces and watching which failures were recoverable and which weren't.

Where I think this goes

Every enterprise now has AI systems in production that nobody can fully characterise. The gap between what a model can do and what an organisation can prove about it is widening, and almost all of the current tooling addresses that gap with documentation rather than enforcement.

I think that's backwards, and I've built the other version. Controls that live in a policy document get routed around within a quarter. Controls that sit inline in the request path — masking, evaluating, recording — survive, provided they don't make the tool slower than the workaround. The hard engineering problem is doing that at latency budgets people will tolerate, which is a systems problem more than a policy one.

The second thing I believe is what pulled me toward harnesses rather than models: as systems become agentic, the attack surface moves off the model and onto the connective tissue — tool registries, context handling, inter-agent trust, the protocols between them. That surface behaves like the network security problems I spent a decade on, and very little like prompt engineering. The teams that do well here will be staffed by people who have run detection and containment at scale, not by people who arrived with the current wave.

Both of these are markets. I've built a production answer to the first, and I own the constraint layer for the second — inside a company where the cost of being wrong was measured in regulatory exposure rather than churn.
